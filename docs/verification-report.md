## 四、L4 端到端阻塞说明

**现象**：模型端点**间歇性**返回 HTTP 524，批量评测无法完成，但**单次短请求正常**。

**五次尝试记录（2026-09-10）**：

| 时间 | 形式 | 结果 |
|---|---|---|
| 12:52 | 单用例 `08-write-script` | ❌ `【模型错误】HTTP 524` |
| 12:57 | 全量 17 用例 | ❌ 前两个用例 524 |
| 13:18 | 单用例 `08-write-script` | ✅ 通过（4 步 / 28,796 tokens） |
| 13:43 | 全量 17 用例 | ❌ 01、02 均 524（会话中断，无完整报告） |
| 13:52 | 单用例 `01-fix-divide` | ✅ 通过（5 步 / 24,315 tokens） |
| 13:53 | 全量 17 用例 | ❌ 01、02 再次 524 |

**证据链**：

1. 评测控制台现在直接打印模型错误（本轮新增的可见性）：
   `❌ 失败【模型错误】模型调用失败（HTTP 524）：openai_error`
2. **反证"代码回归"**：同一时段、同样的任务，**单跑成功 / 批量失败**（13:52 的 01 与
   13:53 全量中的 01 是同一份代码、同一个用例）→ 差异在端点，不在代码
3. 故障窗口内直接探测 `llm.mjs` 的 `chat()`：超时无响应
4. 失败报告留档：`benchmarks/results/2026-09-10T04-52-05-733Z.json`、`...05-14-35-719Z.json`

**归因**：524 是上游网关（Cloudflare 类）的**源站超时**错误。agent 一次任务包含多轮模型调用，
请求体随对话增长，比"单次短请求"更容易触发源站超时——这解释了"短请求成功、长任务失败"的分布。

**处置**：

- 不把这类失败当作能力问题：两次 524 失败报告已提交留档（`3773ade`）
- 在 `benchmarks/run.mjs` 补上**模型错误可见性**——失败行直接标 `【模型错误】`，
  避免下次把"端点故障"误读成"用例失败"
- L4 待端点稳定后重跑：`node benchmarks/run.mjs`

## 六、结论与遗留

**结论**：

1. 代码正确性（L1）、机制完整性（L2）、评测可信度（L3）**三层全部通过**，且 L2/L3 是可复跑的脚本，不是一次性结论
2. 28 项机制每一项都有"可执行的验证"，而不是文档里的声明
3. 评测体系的三道门禁（初始必失败 / 参考修复必通过 / 作弊必被拒）保证了 L4 结论不会被硬编码刷分污染
