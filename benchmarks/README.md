# 基准评测（benchmarks）

用**真实任务**衡量 agent 能力，而不是只看"功能是否实现"。

## 为什么需要

功能测试（`tests/`）只验证"代码没坏"；基准评测验证"任务能不能做成"——这是能力提升的客观标尺。

## 运行

```bash
node benchmarks/run.mjs              # 跑全部用例
node benchmarks/run.mjs 01-fix-divide # 只跑一个
node benchmarks/run.mjs --list       # 列出用例
```

输出：每个用例的通过情况、步数、token 消耗；汇总报告写入 `benchmarks/results/`。

## 用例结构

```
cases/<name>/
  task.md      # 任务描述（喂给 agent）
  setup/       # 初始文件（复制到临时工作目录）
  check.mjs    # 验证：export async function check(cwd) => { passed, detail }
```

## 用例自检（check 的质量门禁）

`check.mjs` 写不好会让评测结果虚高——最典型的是"只比对一组固定输出"，
agent 按 `task.md` 里给出的样例硬编码就能通过。

```bash
node benchmarks/selfcheck.mjs        # 全部用例
node benchmarks/selfcheck.mjs 01 13  # 按名称前缀筛选
```

每个用例跑三道门禁：

| 门禁 | 含义 |
|---|---|
| 初始态必须失败 | 否则用例没测出任何东西 |
| 参考修复必须通过 | 否则 check 会误杀正确解法 |
| 作弊实现必须被拒绝 | 否则评测结论不可信 |

**2026-09-10 审计**：15 个用例中 **12 个原本可被硬编码骗过**——改测试文件、
空测试文件、伪造 npm 脚本输出、硬编码样例输出、空 `formatRow` 等。已全部加固，
现在 15/15 通过自检。常见加固手法：

- 换一组输入重跑（换数据 / 换参数），验证实现通用而非硬编码
- 校验"受保护文件"未被改动（测试、上游数据、README）
- 直接 `import` 目标模块调用，绕开 agent 可写的测试文件
- 变异测试：故意改坏被测函数，测试必须能发现

## 当前结论（2026-09-10）

| 批次 | 用例数 | 通过 | 平均步数 | 总 tokens |
|---|---:|---:|---:|---:|
| 加固前基线（check 有漏洞，结论存疑） | 13 | 13/13 | 7.1 | 352,979 |
| **加固后全量（check 已防作弊）** | 15 | **15/15** | 6.7 | 406,919 |

加固后仍是 15/15，说明之前的通过**不是硬编码刷出来的**，能力是真的；但区分度依然不足：

1. **难度分级**：加入多阶段/长链路任务（大重构、跨仓库改动、需外部环境）
2. **效率指标**：同样通过的情况下，比步数与 token（例如 `15-perf-pair` 用了 9 步 / 38K tokens，明显高于均值）
3. **回归对比**：把评测当门禁，改动后跑一遍，确保通过率不降、token 不涨


## 指标解读

| 指标 | 含义 |
|---|---|
| 通过率 | 任务成功率（最重要） |
| 平均步数 | 效率（步数越少越好） |
| token 消耗 | 成本 |

## 如何扩展

新增用例只需建目录 + 三个文件，无需改运行器：

```bash
mkdir -p benchmarks/cases/09-my-task/setup
# 写 task.md / setup/* / check.mjs
```

## 注意

- 评测会真实调用模型（有 token 成本）
- 网络类任务可能受外部服务波动影响
- `check.mjs` 必须能区分"初始状态"与"完成状态"（先用 setup 跑一遍应失败）
